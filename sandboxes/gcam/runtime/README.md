# GCAM runtime data

Baked into `sandboxes/gcam/Dockerfile`'s final image via `COPY`, not
regenerated on every build. See `docs/sandbox-resource-experiments.md`'s
GCAM section for the full investigation this directory is the result of.

- `exe/` -- small config files (XMLDBDriver.jar/.properties,
  `configuration_*.xml`, `batch_*.xml`, `log_conf.xml`), committed to git
  as-is (~136KB total). `configuration_ref.xml` here is **patched** from
  upstream's default: `xmldb-location`'s `write-output` is `"0"` instead
  of `"1"`. GCAM's own BaseX-backed XML output database needs jars this
  project doesn't ship (found by testing: `SEVERE ERROR: Failed to find
  Java class XMLDBDriver`, then a JVM segfault) -- a separate, unsolved
  problem. Disabling that one output stream (we don't need it; the
  restart file and CSV outputs still write normally) is what let a full
  21-period run (1975-2100) actually complete end-to-end.
- `input/solution/`, `input/policy/`, `input/climate/` -- small supporting
  config directories (~1.5MB total) that `configuration_ref.xml`
  references (solver config, policy-target files, Hector's own
  `hector-gcam.ini`). Committed to git as-is, straight from upstream
  gcam-core.
- `input/gcamdata/xml/` -- **gitignored, not committed** (5.2GB, 221
  files). This is GCAM's actual input database, generated by running
  gcamdata's R data pipeline (`driver_drake()`). Must exist locally here
  before building the final image; see "Regenerating" below.
- `exe/gcam.exe` -- **also gitignored** (294MB binary). Not part of the
  committed Dockerfile's build (that still compiles from source in a
  `builder` stage, same as always), but kept here locally as the exact
  already-compiled, already-validated binary from the successful GPU
  sandbox run -- reused directly (no recompile) when building the
  `possibleplanets/gcam` Docker Hub backup image on a machine too
  memory-constrained to compile GCAM's C++ itself (see
  `docs/sandbox-resource-experiments.md`'s "Backup copy on Docker Hub"
  section for why).

## Public backup: Docker Hub

In addition to the `gcam-production-v1` Daytona snapshot (this project's
primary artifact), a full copy is pushed to **`possibleplanets/gcam:v1`**
(also `:latest`) on Docker Hub, public, as a backup that survives even if
the Daytona snapshot is ever lost. Pull it directly:
`docker pull possibleplanets/gcam:v1` -- `gcam.exe` and the full XML
database are both at the same paths described above
(`/app/gcam-core/exe/gcam.exe`, `/app/gcam-core/input/gcamdata/xml/`).

## Regenerating `input/gcamdata/xml/`

Only needed if: upstream gcam-core/gcamdata's raw data changes, a new bug
needs patching in the pipeline, or the directory is simply missing
locally. This is a one-time (or rare-refresh) step, not something that
runs per request -- confirmed by diffing `configuration_ref.xml` against
`configuration_ssp.xml`: every SSP scenario reads from this exact same
XML set, with scenario-specific variation living in the small `batch_*.xml`
files instead.

1. Build `sandboxes/gcam/gcamdata.Dockerfile` into a Daytona sandbox.
   **This needs a GPU attached purely to unlock a memory ceiling above
   8GB** -- not for GPU compute (R's joins are CPU-only). Confirmed by
   testing: this account's plain CPU sandboxes cap at 8GB memory, and the
   pipeline's `ceds_ghg_en_R_S_T_Y` chunk alone needs more than that to
   complete. A GPU-attached sandbox with `memory: 24` (tested up to 96GB
   accepted) removes that ceiling entirely; peak observed usage during a
   full run was ~13.5GB.
   ```js
   const sandbox = await daytona.create(
     { image: Image.fromDockerfile('sandboxes/gcam/gcamdata.Dockerfile'),
       resources: { cpu: 4, memory: 24, gpu: 1, gpuType: GpuType.L40S },
       autoDeleteInterval: 0 },
     { timeout: 1800 },
   )
   ```
2. Inside that sandbox: `cd /app/gcam-core/input/gcamdata && Rscript -e
   'devtools::load_all(); driver_drake(jobs=1,
   memory_strategy="autoclean", garbage_collection=TRUE,
   caching="worker")'`. `jobs=1` + `autoclean` is load-bearing -- default
   drake parallelism keeps multiple chunks' output resident in memory at
   once, which is strictly worse for this memory-bound pipeline. Took
   ~75 minutes end to end in testing.
3. `tar -czf` the resulting `input/gcamdata/xml/` directory (compresses
   from 5.2GB down to ~430MB -- XML text compresses well) and download it
   with `sandbox.fs.downloadFile()`.
4. Extract into this directory (`sandboxes/gcam/runtime/input/gcamdata/xml/`).
5. Delete the GPU sandbox immediately -- it's billed at a much higher
   rate than this project's normal CPU sandboxes and has no further use
   once the data is downloaded.

Also worth doing while that sandbox is live: compile `gcam.exe` in the
same environment (it already has `git`/`g++`/`make`; just needs
`libboost-dev libeigen3-dev libtbb-dev default-jdk` and the two
submodules per the main Dockerfile's builder stage) and actually run
`./gcam.exe -C configuration_ref.xml` against the freshly-generated
database before trusting it -- that's how the `write-output="0"` patch
above and the missing `input/solution`/`policy`/`climate` directories
were discovered. A `gcam-production-*` Daytona snapshot can be built
straight from `sandboxes/gcam/Dockerfile` once this directory is
populated, without needing a GPU at all (the final image only runs
`gcam.exe`, which is plain CPU compute).
