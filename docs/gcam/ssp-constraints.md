# GCAM SSP scenario naming and why they're unconstrained baselines

## The problem this fixes

Before this change, GCAM exposed 5 SSP scenarios using its own native
narrative names: `SSP1`, `SSP2`, `SSP3`, `SSP4`, `SSP5`. Every other model on
the dashboard (hector, fair, oscar, twolayer) uses CMIP6/ScenarioMIP-style
names that combine an SSP narrative with a specific forcing target by 2100,
e.g. `ssp126`, `ssp245`, `ssp370`, `ssp460`, `ssp585`. `lib/clientApi.ts`'s
`SSP_CANONICAL` map groups/highlights runs across models by these codes, so
GCAM's old `SSP1`..`SSP5` strings never matched anything and never grouped
with the same-conceptual-family runs from the other models on the chart's
SSP legend.

The fix: GCAM's 5 scenario configs are renamed to the matching canonical
codes (`ssp126`, `ssp245`, `ssp370`, `ssp460`, `ssp585`) so they group
correctly. See `sandboxes/gcam/run.py`'s `SUPPORTED_SCENARIOS` dict and
`docs/gcam/ssp-scenarios.md` for how the underlying config files are built.

## Why they're still unconstrained narrative baselines, not real forcing targets

A CMIP6 code like `ssp126` means two separate things bundled into one name:
an SSP socioeconomic narrative (population, GDP, technology assumptions) AND
a specific radiative-forcing target by 2100 (here, 2.6 W/m²) that a climate
policy (typically a carbon price) is assumed to hit. hector/fair/oscar/
twolayer's `ssp1xx`-style scenarios actually apply that forcing constraint.

GCAM's `find-path` config option is the mechanism that would do the same:
when `find-path=1`, GCAM's "Policy Target Runner" searches for a carbon
price path that drives the model's own forcing trajectory to match
`policy-target-file`'s target, instead of just running the SSP narrative
forward with no climate policy at all.

Two of the five target codes don't need this at all: ScenarioMIP's own
definition of `ssp370` (7.0 W/m² by 2100, SSP3) and `ssp585` (8.5 W/m²,
SSP5) is each narrative's own "no additional climate policy" baseline. For
those, `find-path=0` with no constraint already *is* correct and this
project leaves them that way.

The other three (`ssp126` at 2.6, `ssp245` at 4.5, `ssp460` at 6.0) do need
a real constraint to be accurate. This project shipped the policy-target
files for them (`sandboxes/gcam/runtime/input/policy/forcing_target_2p6_
overshoot.xml`, `forcing_target_4p5.xml`, `forcing_target_6p0.xml`) and
tried `find-path=1` against each, live, in this sandbox.

## What the live test found

All three ran to completion of GCAM's normal model solve multiple times —
each "Policy Target Runner: scenario dispatch #N" cycle independently
solved all 21 periods cleanly ("All model periods solved correctly. Model
run completed.") — but after 3-4 such dispatch cycles (the Policy Target
Runner using each dispatch's resulting forcing to compute its next trial
carbon price), GCAM itself threw:

```
ERROR:Failed due to invalid trial price generated by solver.
```

This happened on every scenario tested this way (`ssp126` and `ssp460`
were run to this exact failure; `ssp245` was still mid-run when the other
two had already failed identically twice). Cgroup memory sat at the
sandbox's 8GB ceiling throughout (`oom_kills: 0` both times checked — this
is NOT an out-of-memory kill), so this is a genuine non-convergence of
GCAM's own carbon-price bisection search for these specific targets/
narratives combinations in this environment, not a configuration mistake
and not a resource-limit artifact.

Given that, `find-path` was reverted to `0` on all three. The
`policy-target-file` entries are left in place (pointed at the correct
targets) purely for documentation/future reference, but they're inert
while `find-path=0`.

## Net effect

All 5 GCAM SSP scenarios (`ssp126`/`ssp245`/`ssp370`/`ssp460`/`ssp585`) are
unconstrained narrative baselines — identical in spirit to the original
`SSP1`-`SSP5`, just renamed to group correctly with the other models' same-
narrative-family runs on the shared SSP legend. They do NOT represent the
same real-world forcing trajectory as the hector/fair/oscar/twolayer runs
of the same name for the 3 scenarios where ScenarioMIP's own target implies
a policy constraint (`ssp126`, `ssp245`, `ssp460`); they do, for `ssp370`/
`ssp585`, where the marker's definition is itself the unconstrained
baseline.

## If someone wants to revisit real constraint enforcement later

Possible directions, untried here:
- A different/looser policy-target-file (e.g. a less aggressive overshoot
  path for 2.6) might converge where the shipped one didn't — not tested.
- GCAM has alternate target-finder settings (bisection tolerance, max
  iterations) beyond what this project's configs touch — not explored.
- Running outside this sandbox's 8GB ceiling, with more memory headroom,
  might change the outcome even though the observed failure wasn't a raw
  OOM — not tested, since this project's production tier is fixed at 8GB.
